## Background: what is a memory leak?

Picture a parking lot, where every car drives in and eventually drives out. The wrecks always get towed to the scrapyard. Now imagine the lot never empties, or empties too slowly, and ends up saturated. We have a problem: new cars have nowhere to park.

In the JVM, every object uses a small amount of memory, quickly freed by the garbage collector once the object is no longer referenced. Sometimes, though, unused objects live on indefinitely.

These objects pile up and eventually block future allocations the application needs to run. The danger of memory leaks is that they often slip through testing and quality assurance — they tend to surface after the application has been running for weeks, sometimes long after the triggering code shipped to production.

## Phase 1 — Reproducing the leak

**Starting conditions.** At the moment of the crash, there was no visibility into the heap state: no metrics, no dump, no profiling data from the production instance. The investigation started from zero.

**Goal.** Simulate the load that triggered the crash on controlled infrastructure, confirm heap usage climbs, and produce a repeatable test to verify any future fix.

A first, simplistic approach would be to write a script in Bash or Python to fire requests automatically. We needed something more precise: a realistic simulation of the very short, intense load spike that characterises our application's real traffic. We used [Gatling](https://gatling.io/), an open-source load-testing tool with a Java SDK.

With the Gatling scenario running, we observed heap usage via `jstat` and the IntelliJ profiler over JMX. The result was unambiguous: **heap usage climbed steadily toward the container memory limit** and did not stabilise.

> **Evidence needed — heap-growth graph:** A screenshot of the memory monitor captured during the Gatling run — heap used vs. time, annotated with the load-test window and the container memory limit — would make the climb immediately visible rather than asserted. See `evidence/content/memory-leak-evidence-needed.md` item E-2.

## Phase 2 — Instrumentation

Our infrastructure runs a JRE (not a full JDK) on Alpine Linux to keep Docker images small. Disk space inside the container was very tight. Those two constraints shaped every tool choice.

| Tool | Role | Why chosen |
|------|------|-----------|
| [Gatling](https://gatling.io/) | Load generation | Realistic HTTP traffic with repeatable, measurable scenarios; Java SDK |
| `jstat` / `jmap` | Quick heap stats | Bundled with JDK — not available in this environment (JRE only) |
| [jattach](https://github.com/jattach/jattach) | Heap dump capture | Standalone binary, minimal footprint; works on JRE-only Alpine containers |
| IntelliJ profiler / VisualVM | Heap dump analysis and flamegraph | GUI analysis of `.hprof` files; allocation flamegraph view |
| JMX standard | Live heap metrics | Works with JRE; readable by VisualVM and IntelliJ |

**Why not `jmap`?** `jmap` ships with the JDK. Our container carried a JRE only. `jattach` replicates the `dumpheap` command via the JVM attach API, which is accessible from any process with the right OS permissions — no JDK required, and the resulting `.hprof` file is identical.

## Phase 3 — Evidence collection

### 3a. Heap dump

A heap dump is a snapshot of all JVM memory allocations at a precise instant. It records every live object, its class, its size, and the references between objects. The file format is `.hprof`.

We captured it with `jattach`:

```sh
jattach <pid> dumpheap /tmp/heap.hprof
```

We then loaded the dump into the IntelliJ profiler. Sorting by **Retained** memory, `ConcurrentHashMap` appeared at the top of the class list.

Three columns drive this analysis:

| Column | Meaning |
|--------|---------|
| Count | Number of live instances of this class |
| Shallow | Memory the objects occupy directly |
| Retained | Memory freed if all instances were collected, including every object they reference |

Data-collection objects — Maps, Lists — routinely top the Retained column because their job is to hold references to other objects. The challenge is tracing *who put objects into the map*, and *who should have removed them*.

> **Evidence needed — heap dump object table:** A screenshot (or exported CSV) of the Objects tab in IntelliJ profiler or Eclipse MAT, sorted by Retained size descending, showing `ConcurrentHashMap` at or near the top, constitutes the primary evidence for this step. See `evidence/content/memory-leak-evidence-needed.md` item E-3.

### 3b. Flamegraph

A flamegraph plots each method call as a rectangle; the rectangle's width is proportional to the memory it allocated during the profiling window. Wide rectangles are where allocations concentrate.

We captured the flamegraph with the IntelliJ profiler during a Gatling run.

> **Evidence needed — flamegraph image:** The flamegraph is the single most important piece of evidence in this investigation. It should show `Thread.run` as the entry point and `io.sentry.transport.HttpConnection.createConnection` spanning approximately 50 % of the total allocation width. See `evidence/content/memory-leak-evidence-needed.md` item E-4.

**What the flamegraph showed.** The entry point was `Thread.run`. Walking down the call tree, `io.sentry.transport.HttpConnection.createConnection` was by far the widest rectangle. Switching to a callers view, we traced the chain:

1. Every inbound HTTP request to our application triggered the Spring `FilterChain`.
2. The `FilterChain` invoked a Sentry performance-tracing hook.
3. That hook called `io.sentry.transport.HttpConnection.createConnection`, which stored performance data in a `ConcurrentHashMap`.
4. The map was never drained — entries accumulated for every request, retaining all the objects they referenced.

## Phase 4 — Hypotheses

### Hypothesis A — The leak originates in our application code

**Status: discarded.**

Our first instinct was to look for application-layer mistakes: missing `close()` calls, static collection fields accumulating data, or sessions not expiring. The heap dump and flamegraph ruled this out quickly. Every allocation hot-spot sat entirely inside the Sentry SDK, not in any class we owned.

### Hypothesis B — The Sentry SDK has a resource-management bug

**Status: confirmed.**

The flamegraph pointed directly at `io.sentry.transport.HttpConnection.createConnection`. The `ConcurrentHashMap` growing in retained memory was inside the SDK's transport layer — performance data queued for upload to the Sentry platform that was never flushed or evicted.

**Verification step.** We disabled the Sentry SDK entirely and replayed the Gatling scenario. Heap usage stabilised. This isolated the SDK as the sole variable and confirmed our hypothesis.

> **Evidence needed — before/after heap graphs:** A side-by-side comparison of heap-usage graphs — one with Sentry enabled (climbing) and one with Sentry disabled (stable) — would convert this confirmation step from narrative to visual evidence. See `evidence/content/memory-leak-evidence-needed.md` item E-5.

Searching the `sentry-java` issue tracker, we found [issue #2496](https://github.com/getsentry/sentry-java/issues/2496), which described exactly our symptom in version 6.12.1.

---

## Phase 5 — Root cause

**Affected version:** Sentry Java SDK 6.12.1.

**Mechanism.** The SDK's HTTP transport layer opened a connection and stored performance-tracing data in a `ConcurrentHashMap` for every request passing through the Spring `FilterChain`. In version 6.12.1, a bug prevented the map from being drained after the data was sent. Entries accumulated indefinitely, retaining all referenced objects, until the heap exhausted available space.

**Upstream acknowledgement.** The bug is documented in [sentry-java issue #2496](https://github.com/getsentry/sentry-java/issues/2496) and fixed in [pull request #2505](https://github.com/getsentry/sentry-java/pull/2505), merged into version 6.13.

---

## Phase 6 — Fix

A one-line change in the dependency manifest:

```
# Before
io.sentry:sentry-spring-boot-starter:6.12.1

# After
io.sentry:sentry-spring-boot-starter:6.13.0
```

No application code required changes. The fix was entirely in the third-party library.

---

## Phase 7 — Verification

**Step 1 — Disable Sentry.** Replaying the Gatling scenario with Sentry fully disabled confirmed that heap usage was stable (see Hypothesis B). This proved the SDK was the sole cause.

**Step 2 — Update and replay.** After bumping to 6.13, we re-ran the same Gatling scenario. Heap usage remained stable over the full test duration. The `ConcurrentHashMap` retained size did not climb.

**Step 3 — Production deployment.** The updated SDK shipped to production. The application remained stable under identical traffic.

> **Evidence needed — post-fix heap graph:** A heap-usage graph from the same Gatling scenario with SDK 6.13 — ideally shown alongside the pre-fix graph — would close the evidentiary loop. See `evidence/content/memory-leak-evidence-needed.md` item E-6.

*An ironic footnote: Sentry — the tool that caused the crash — was the one that alerted us to the `OutOfMemoryError` in the first place.*

## Reusable investigation method

The following five-step sequence generalises to any JVM memory-leak investigation:

1. **Collect what you can at the crash site.** Enable `-XX:+HeapDumpOnOutOfMemoryError` before incidents, not after. Logs, metrics, and a heap dump captured at the moment of failure are worth more than any post-mortem reconstruction.

2. **Reproduce the leak on controlled infrastructure.** A scripted load test — [Gatling](https://gatling.io/), JMeter, k6 — that reliably triggers climbing heap usage gives you a repeatable experimental apparatus.

3. **Capture and analyse a heap dump.** Sort by Retained memory. Data-collection classes (Maps, Lists) at the top are common, but they are symptoms — trace object ownership to find the allocating code.

4. **Capture a flamegraph.** The flamegraph converts the ownership question into a call-stack question. The widest rectangle in the allocation view is your primary suspect.

5. **Confirm by isolation, then fix.** Disable or replace the suspect; replay the load test. Only when the symptom disappears do you have confirmation. Fix, re-run, deploy.

## Prevention

The best fix is the one you never need:

- **Know your limits.** Load-test at nominal *and* peak-realistic load. Memory leaks rarely surface under everyday conditions alone.
- **Stay current on dependencies.** This entire incident was a known SDK bug. Tools like [Dependabot](https://github.com/dependabot) keep libraries up to date automatically.
- **Use static analysis.** Tools such as *SonarQube* flag patterns likely to cause leaks — unclosed resources, growing static collections.
- **Add observability.** Heap metrics and alerting (Datadog, an ELK stack) let you catch a climbing baseline before the application crashes.
- **Arm the JVM.** Add `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/` to your JVM flags in every environment. A heap dump captured at crash time is the fastest path to a root cause.
